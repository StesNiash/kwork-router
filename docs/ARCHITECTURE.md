# Архитектура kwork-router

## Роль

`kwork-router` — единый репозиторий карточек Kwork и машинночитаемой таблицы направлений. Сайта нет: вход — `README.md`, полные тексты — в `cards/`, демо — в отдельных репозиториях `kwork-*`.

- `README.md` — человеческая таблица карточек;
- `FORMAT.md` — поля, лимиты и шаблон карточки Kwork;
- `TAXONOMY.md` — дерево Kwork: рубрика → подрубрика → тип → вид;
- `data/services.json` — та же таблица для проверок и автоматизации;
- `data/kwork-taxonomy.json` — исходная структура рубрик;
- `cards/` — полные описания, FAQ и промпты обложек;
- демо-репозитории — код, тесты и доказательство выполнения.

## Структура

```text
kwork-router/
├── README.md          # таблица карточек
├── FORMAT.md          # формат и лимиты полей
├── TAXONOMY.md        # справочник Kwork
├── data/
│   ├── services.json
│   └── kwork-taxonomy.json
├── cards/             # описания и промпты обложек
├── docs/              # решения и границы
├── tests/             # контракт данных и отсутствие секретов
├── KWORK.md           # что можно обещать покупателю
└── PORTFOLIO.md
```

## Статусы

```text
planned → ready → active
```

- `planned` — направление заявлено, репозитория ещё нет;
- `ready` — демо и тесты готовы, карточка не опубликована;
- `active` — карточка опубликована на Kwork.

## Связь с семействами

```text
kwork-router (таблица + карточки)
   ├── kwork-hermes-vps      active  → установка Hermes
   ├── kwork-parser          ready   → парсеры и выгрузки
   ├── kwork-tg-bot          ready   → Telegram-боты
   ├── kwork-sheets          ready   → Google Sheets / Apps Script
   ├── kwork-python-scripts  ready   → небольшие утилиты
   ├── kwork-monitor         planned → мониторинг
   ├── kwork-api-sync        planned → API-синхронизация
   └── kwork-ai-rag          planned → RAG/ассистенты
```

Один демо-репозиторий может закрывать несколько карточек. Например, `kwork-tg-bot` — заявки, FAQ и оплату. Но текст карточки остаётся в `cards/`.

## Контракт данных

Каждое семейство в `data/services.json` обязано иметь:

- `id` — стабильный идентификатор;
- `number` — номер карточки в реестре;
- `title`, `summary`;
- `repo` — имя отдельного репозитория;
- `status` — `active`, `ready` или `planned`;
- `wave` — очередь публикации;
- `price_from`, `term`;
- `bullets`, `demo`, `tone`;
- `card` — путь к файлу карточки (пусто для `planned`);
- `repo_url` — ссылка на GitHub-репозиторий (пусто для `planned`).

Карточка в `cards/` следует `FORMAT.md`: `Название`, `Рубрика` → `Подрубрика` → `Тип` → `Вид`, обложка **660×440 (3:2)**, `Описание`, `От покупателя нужно`, `Стоимость и опции`, `Дополнительные опции` и `FAQ`.

Тест проверяет уникальность `id` и `number`, допустимые статусы, наличие файлов карточек, обязательные разделы, лимиты опций (40/100), промпты обложек и GitHub-ссылки.

## Границы

- Нет сайта, сборки и фронтенда.
- Репозиторий не хранит токены, клиентские данные и ключи.
- Демо-репозитории не дублируют тексты карточек.
- `planned` не значит «готово»: ссылка на демо появляется только после тестов.
- Цены в JSON — черновые, для карточки и брифа.
