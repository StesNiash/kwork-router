# Архитектура kwork-router

## Роль

`kwork-router` — единый источник правды по карточкам Kwork и витрина направлений. Он не содержит бизнес-логики парсеров, ботов и установщиков.

- `cards/` — полные тексты карточек, FAQ и промпты обложек;
- `data/services.json` — краткий реестр для витрины и ссылка на файл карточки;
- демо-репозитории `kwork-*` — код, тесты и доказательство выполнения.

## Слои

```text
kwork-router/
├── index.html          # оболочка витрины
├── styles.css          # оформление
├── app.js              # рендер карточек из JSON и фильтры
├── data/services.json  # реестр семейств и ссылки
├── cards/              # описания карточек и промпты обложек
├── docs/               # решения и границы
├── tests/              # контракт данных и отсутствие секретов
└── KWORK.md            # что можно обещать покупателю
```

## Почему витрина data-driven

- `index.html` не дублирует 8 карточек вручную;
- `app.js` рендерит карточки из `data/services.json`;
- при изменении цены или статуса правится один JSON;
- полный текст карточки лежит в `cards/` и не размазан по демо-репозиториям.

## Статусы

```text
planned → ready → active
```

- `planned` — направление заявлено, репозитория ещё нет;
- `ready` — демо и тесты готовы, карточка не опубликована;
- `active` — карточка опубликована на Kwork.

Фильтр «Готово» показывает `active` и `ready`.

## Связь с семействами

```text
kwork-router (карточки + витрина)
   ├── kwork-hermes-vps      active  → установка Hermes
   ├── kwork-parser          ready   → парсеры и выгрузки
   ├── kwork-tg-bot          ready   → Telegram-боты
   ├── kwork-sheets          ready   → Google Sheets / Apps Script
   ├── kwork-python-scripts  ready   → небольшие утилиты
   ├── kwork-monitor         planned → мониторинг
   ├── kwork-api-sync        planned → API-синхронизация
   └── kwork-ai-rag          planned → RAG/ассистенты
```

Один демо-репозиторий может закрывать несколько карточек. Например, `kwork-tg-bot` — заявки, FAQ и оплату. Но текст карточки остаётся в `cards/`.

## Контракт данных

Каждое семейство в `data/services.json` обязано иметь:

- `id` — стабильный идентификатор;
- `number` — номер карточки в реестре;
- `title`, `summary`;
- `repo` — имя отдельного репозитория;
- `status` — `active`, `ready` или `planned`;
- `wave` — очередь публикации;
- `price_from`, `term`;
- `bullets`, `demo`, `tone`;
- `card` — путь к файлу карточки (пусто для `planned`);
- `repo_url` — ссылка на GitHub-репозиторий (пусто для `planned`).

Тест проверяет уникальность `id` и `number`, допустимые статусы, наличие файлов карточек и GitHub-ссылок.

## Границы

- Витрина не хранит токены, клиентские данные и ключи.
- Демо-репозитории не дублируют тексты карточек.
- `planned` не значит «готово»: ссылка на демо появляется только после тестов.
- Цены в JSON — черновые, для карточки и брифа.
